# BLE Studio capture and reverse-engineering research

**Scope.** This report is implementation research for a Kotlin/Compose Android tablet app that captures and explains BLE traffic, explores GATT, labels/replays commands, and exports evidence. Facts marked **[PROVEN]** are directly supported by the cited AOSP, Android Developers, Bluetooth SIG, or GitHub source. Facts marked **[INFERENCE]** are engineering conclusions that must be verified on the owner’s tablet/phone and OEM build.

## 1. Android HCI snoop capture

### What Android captures

**[PROVEN]** Android’s Bluetooth debugging documentation describes BTSnoop as an HCI packet capture and says that most devices store logs below `data/misc/bluetooth/logs`; it also says that always-on in-memory BTSnoop is privacy-filtered and that enabling **Enable Bluetooth HCI snoop log** in Developer options requires restarting Bluetooth before logging takes effect. Source: [AOSP Verify and debug](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging).

**[INFERENCE]** HCI snoop is local to the Android controller/host boundary. It can capture traffic generated by an Android vendor app running on that phone, but it cannot passively decode an iPhone↔gadget connection merely because the tablet is nearby. iOS traffic requires an external over-the-air sniffer or a proxy/MITM.

### Modes and property

**[PROVEN]** The AOSP property is:

```text
persist.bluetooth.btsnooplogmode
```

The Settings controller maps list entries to `disabled`, `filtered`, and `full`, and writes that exact system property. Source: [AOSP BluetoothSnoopLogPreferenceController.java](https://raw.githubusercontent.com/aosp-mirror/platform_packages_apps_Settings/master/src/com/android/settings/development/BluetoothSnoopLogPreferenceController.java).

**[PROVEN]** Current AOSP Bluetooth sysprop metadata declares `persist.bluetooth.btsnoopdefaultmode` and `persist.bluetooth.btsnooplogmode` with enum values `empty|disabled|filtered|full`. `empty` means unset/default selection, not an operational capture mode. The current logger additionally recognizes `kernel` as an implementation mode. Source: [BluetoothProperties.sysprop](https://android.googlesource.com/platform/system/libsysprop/+/refs/heads/main/srcs/android/sysprop/BluetoothProperties.sysprop) and [current Gabeldorsche snoop_logger.cc](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger.cc).

| Mode | AOSP behavior | BLE reverse-engineering consequence |
|---|---|---|
| `disabled` | Deletes/does not write ordinary snoop files; AOSP still documents a privacy-limited in-memory path on builds that provide it. ([AOSP docs](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging), [logger](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger.cc)) | Do not expect arbitrary vendor command payloads. |
| `filtered` | Enables stack filters and uses a filtered log path. AOSP sysprop comments state that non-fragment ACL packets may be truncated to a fixed maximum and that profile-specific filters can discard or redact A2DP, MAP, PBAP, HFP, and RFCOMM data. ([sysprop](https://android.googlesource.com/platform/system/libsysprop/+/refs/heads/main/srcs/android/sysprop/BluetoothProperties.sysprop), [logger](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger.cc)) | Discovery may look plausible while long custom writes are incomplete. Treat included length and packet payload as authoritative; do not use this mode for protocol extraction. |
| `full` | Disables the filtered logger and writes unfiltered HCI records to the regular log. ([logger](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger.cc)) | Recommended mode for arbitrary vendor GATT commands. **[INFERENCE]** It should expose bytes present at Android’s HCI host boundary; confirm by finding ATT writes in the parsed output. |
| `kernel` | Recognized by current logger as a kernel logging mode, but not offered by the Settings list above. ([logger](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger.cc)) | OEM/controller-specific; do not expose as the default UI choice. |

**[PROVEN]** AOSP’s file logger creates the configured snoop directory with a Bluetooth group and rotates the active file to a `.last` suffix; the actual base path is supplied by `ParameterProvider`, so `/data/misc/bluetooth/logs/btsnoop_hci.log` is a common path, not an API guarantee. Source: [snoop_logger_file.cc](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger_file.cc) and [AOSP debugging docs](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging).

### Recommended clean capture procedure

1. Make the vendor phone/tablet the only active BLE actor, stop unrelated BLE apps, and record `getprop ro.build.version.sdk`, `getprop ro.build.fingerprint`, Bluetooth adapter address (if available), and app package.
2. Select **Full** in Developer options’ Bluetooth HCI snoop setting. The AOSP Settings controller writes `persist.bluetooth.btsnooplogmode`; no app-facing Android API is promised for this property. ([Settings source](https://raw.githubusercontent.com/aosp-mirror/platform_packages_apps_Settings/master/src/com/android/settings/development/BluetoothSnoopLogPreferenceController.java)).
3. Restart Bluetooth. The UI documentation explicitly requires this. ([AOSP docs](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging)).
4. Start the vendor app, connect, and perform one labelled action at a time. Keep a human action log with wall-clock timestamps; HCI records do not carry Android app identity.
5. Capture a bugreport immediately after the action set, then parse the returned `.btsnoop`/`.log` and preserve the untouched original as evidence.

## 2. Bugreportz, dumpsys, and btsnooz extraction

### Bugreport commands

**[PROVEN]** `bugreportz` produces a zipped bugreport and returns the path using a simple protocol. `bugreportz -p` emits `BEGIN:<path>` followed by progress and `OK:<path>`/`FAIL:<error>`; `bugreportz -s` streams the zip to stdout. Sources: [bugreportz README](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/cmds/bugreportz/readme.md), [main.cpp](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/cmds/bugreportz/main.cpp?format=TEXT), and [Android bug-report guide](https://developer.android.com/studio/debug/bug-report).

For a Shizuku UserService, prefer:

```text
bugreportz -s
```

and stream stdout in bounded chunks into the app’s private storage. `bugreportz -p` is useful when the service wants a path/progress protocol, but the path may be in a shell-owned location. **[INFERENCE]** An OEM can change output locations; consume the returned protocol rather than hard-coding `/data/user_de/0/com.android.shell/files/bugreports`.

**[PROVEN]** Android’s bugreport documentation says the zip contains a main text report plus filesystem copies under an `FS` directory where included files retain their source path below `FS/`. That does not guarantee every Bluetooth log file is copied; use the BTSNOOP summary path when present. Source: [Android bug-report guide](https://developer.android.com/studio/debug/bug-report).

### BTSNOOP_LOG_SUMMARY and btsnooz

**[PROVEN]** The AOSP `btsnooz.py` tool searches bugreport text for:

```text
--- BEGIN:BTSNOOP_LOG_SUMMARY
...
--- END:BTSNOOP_LOG_SUMMARY
```

It concatenates base64 lines, decodes a custom format consisting of an uncompressed file header followed by zlib-compressed records, and writes a normal btsnoop file. It supports btsnooz versions 1 and 2, converts internal packet types to HCI type bytes, and emits a standard header with magic `btsnoop\0`, version `1`, and datalink `1002`. Source: [AOSP btsnooz.py](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/tools/scripts/btsnooz.py).

**[PROVEN]** AOSP explicitly instructs engineers to run `btsnooz.py BUG_REPORT.txt > BTSNOOP.log` to extract the snoop stream. Source: [AOSP Verify and debug](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging).

**Answer to whether Gabeldorsche embeds btsnooz.** **[PROVEN]** The AOSP bugreport integration is designed to expose a base64 `BTSNOOP_LOG_SUMMARY` section for `btsnooz.py`; the exact presence and source of that section are build/version dependent. **[INFERENCE]** A bare `dumpsys bluetooth_manager` may or may not include the marker on an OEM build; the robust implementation is to request a full bugreport and scan every text member for the markers rather than relying on one dumpsys output shape.

**Full versus filtered payload.** **[PROVEN]** The decoder itself is mode-agnostic: it converts whatever records the stack supplied. The ordinary logger’s `full` and `filtered` paths are distinct, and `filtered` applies truncation/redaction rules. ([btsnooz.py](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/tools/scripts/btsnooz.py), [BluetoothProperties.sysprop](https://android.googlesource.com/platform/system/libsysprop/+/refs/heads/main/srcs/android/sysprop/BluetoothProperties.sysprop), [logger](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger.cc)). Therefore, marker presence is not proof of complete vendor payloads; enforce `full`, then verify that ATT write records contain expected lengths.

### Direct file access and SELinux

**[PROVEN]** Current AOSP policy labels a separate `bluetooth_logs_data_file` type and grants the `bluetooth` domain directory/file creation and write permissions. It also lets the Bluetooth domain read `shell_data_file` bugreport descriptors. Source: [AOSP private/bluetooth.te](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/bluetooth.te). The file logger comments expect a directory grouped as `bluetooth`. ([snoop_logger_file.cc](https://chromium.googlesource.com/aosp/platform/packages/modules/Bluetooth/+/HEAD/system/gd/hal/snoop_logger_file.cc)).

**[INFERENCE]** A shell-UID Shizuku process should not assume it can `cat` `/data/misc/bluetooth/logs/*`: DAC group membership and SELinux policy vary by device, and the current AOSP policy does not grant a generic shell-domain rule for `bluetooth_logs_data_file`. Use `bugreportz -s`/`btsnooz` first. If direct reading is attempted, capture its exact error and retain the bugreport fallback.

    implementation("dev.rikka.shizuku:api:13.1.5")

```

Sources: [Shizuku-API README](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/README.md), [Maven Central api page](https://central.sonatype.com/artifact/dev.rikka.shizuku/api).

    android:authorities="${applicationId}.shizuku"
    android:multiprocess="false"
    android:enabled="true"

```

Source: [Shizuku-API README](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/README.md).

### Permission and identity

**[PROVEN]** Shizuku reports UID `0` for root and UID `2000` for the ADB/shell backend. The README emphasizes that Android permissions, Linux UID/capabilities, and SELinux all matter; shell cannot access arbitrary app data. Source: [Shizuku-API README](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/README.md).

**[PROVEN]** AOSP’s `com.android.shell` manifest includes `DUMP`, `BLUETOOTH`, `BLUETOOTH_ADMIN`, `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT`, `BLUETOOTH_ADVERTISE`, `GRANT_RUNTIME_PERMISSIONS`, and other tool permissions. Permissions can vary by Android release/OEM. Source: [AOSP Shell AndroidManifest.xml](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/packages/Shell/AndroidManifest.xml).

**[INFERENCE]** This makes Shizuku shell suitable for invoking `dumpsys`, `bugreportz`, `logcat`, `am`, and many Bluetooth shell operations, but it does not turn the app into root and does not guarantee direct access to Bluetooth-private files.

### UserService design

**[PROVEN]** The Shizuku README recommends `UserService` over the deprecated text-oriented `newProcess` path. A UserService runs in a separate process as shell UID `2000` when Shizuku is ADB-backed, can implement an AIDL `IBinder`, and must implement the reserved destroy transaction (`16777114` in AIDL / `16777115` transaction code) and exit itself. Source: [Shizuku-API README](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/README.md).

Use a UserService to:

- execute `bugreportz -s` with `ProcessBuilder`;
- stream stdout in chunks over a small AIDL interface (`readChunk`, `cancel`, `getExitCode`);
- optionally attempt direct log reads and report errno/SELinux failure;
- run `dumpsys bluetooth_manager`, `logcat`, and `cmd bluetooth_manager help`.

**[PROVEN]** The official Shizuku demo implements exactly this architecture: `DemoActivity` constructs `Shizuku.UserServiceArgs`, calls `bindUserService`, and receives an AIDL stub; `UserService` returns `pid`/`uid` and implements `destroy()`/`System.exit(0)`. Sources: [DemoActivity.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/demo/src/main/java/rikka/shizuku/demo/DemoActivity.java), [UserService.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/demo/src/main/java/rikka/shizuku/demo/service/UserService.java), [IUserService.aidl](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/demo/src/main/aidl/rikka/shizuku/demo/IUserService.aidl).

### BLE permissions for BLE Studio itself

**[PROVEN]** For target SDK 31+, Android requires runtime `BLUETOOTH_SCAN`, `BLUETOOTH_ADVERTISE`, and `BLUETOOTH_CONNECT` for scanning, advertising, and communicating with paired devices. `BLUETOOTH_SCAN` may use `android:usesPermissionFlags="neverForLocation"` only when the app can strongly assert it never derives location. Source: [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions).

## 4. btsnoop parser and GATT reconstruction

### btsnoop framing

**[PROVEN]** AOSP’s btsnooz converter writes this 16-byte standard header:

```text
62 74 73 6e 6f 6f 70 00  00 00 00 01  00 00 03 ea
b t s n o o p \0         version=1  datalink=1002 (H4)
```

Its packet records use big-endian fields: original length (`u32`), included/captured length (`u32`), flags (`u32`), drops (`u32`), timestamp (`u64`), then the HCI packet bytes. AOSP’s legacy implementation shows the same 24-byte record header and uses network-byte-order conversion. Sources: [AOSP btsnooz.py](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/tools/scripts/btsnooz.py), [AOSP legacy btsnoop.cc](https://android.googlesource.com/platform/system/bt/+/android-9.0.0_r7/hci/src/btsnoop.cc), and [RFC 1761](https://www.rfc-editor.org/rfc/rfc1761).

Parser requirements:

```text
read 16-byte file header
assert magic == btsnoop\0
read version and datalink as big-endian
for each record:
    read 24-byte big-endian record header
    reject included_length > remaining bytes
    retain raw bytes and parse only included_length
    advance by 24 + included_length (+ any format-specific padding)
```

Preserve original length versus included length; a mismatch is direct evidence of truncation, which is especially important for filtered logs.

### HCI H4 and ACL

**[PROVEN]** H4 packet type bytes are `0x01` command, `0x02` ACL data, `0x03` SCO, `0x04` event, and `0x05` ISO. The AOSP btsnooz script maps internal incoming/outgoing types to these bytes. Source: [AOSP btsnooz.py](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/tools/scripts/btsnooz.py).

For HCI ACL data, decode the 4-byte little-endian header:

```text
handle_pb_bc : u16 LE  (handle = low 12 bits; PB/BC flags in upper bits)
data_length  : u16 LE
payload       : data_length bytes
```

The open-source [NCC BLE-Replay btsnoop module](https://raw.githubusercontent.com/nccgroup/BLE-Replay/master/btsnoop/README.md) demonstrates H4 and ACL parsing and then dispatches ACL payloads to L2CAP and ATT parsers.

### L2CAP and ATT

**[PROVEN]** GATT runs over the ATT bearer carried by L2CAP, and the Bluetooth SIG specification says multi-octet ATT fields are little-endian except characteristic value bytes whose encoding is defined by the higher layer. Sources: [Bluetooth SIG ATT](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/attribute-protocol--att-.html), [Bluetooth SIG GATT](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/generic-attribute-profile--gatt-.html).

For a basic LE ACL packet, decode:

```text
l2cap_length : u16 LE
cid          : u16 LE
l2cap_data   : l2cap_length bytes
```

The fixed ATT CID is `0x0004`; ignore non-ATT CIDs while retaining them as raw evidence. **[PROVEN]** The Bluetooth SIG ATT specification defines requests, responses, commands, notifications, indications, and confirmations and says write commands do not generate responses. ([ATT specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/attribute-protocol--att-.html)).

Useful ATT opcodes:

| Opcode | PDU |
|---:|---|
| `0x04` / `0x05` | Find Information request / response |
| `0x08` / `0x09` | Read By Type request / response |
| `0x0A` / `0x0B` | Read request / response |
| `0x10` / `0x11` | Read By Group Type request / response |
| `0x12` / `0x13` | Write Request / Write Response |
| `0x1B` | Handle Value Notification |
| `0x1D` | Handle Value Indication |
| `0x52` | Write Command (write without response) |

Sources: [Bluetooth SIG ATT opcode summary](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/attribute-protocol--att-.html), [NCC BLE-Replay parser README](https://raw.githubusercontent.com/nccgroup/BLE-Replay/master/btsnoop/README.md).

### Mapping handles back to UUIDs

Do not label a write from an HCI handle alone. Build a connection-scoped attribute map:

1. **Primary services.** Parse `ATT_READ_BY_GROUP_TYPE_RSP` (`0x11`) for requests using type `0x2800` (Primary Service). Each element gives a start handle, end handle, and 16- or 128-bit service UUID. Secondary service type is `0x2801`.
2. **Characteristics.** Within each service handle range, parse `ATT_READ_BY_TYPE_RSP` (`0x09`) for type `0x2803` (Characteristic declaration). The value is properties (`u8`), characteristic value handle (`u16 LE`), and characteristic UUID (`u16` or 128-bit).
3. **Descriptors.** For each characteristic value handle, parse `ATT_FIND_INFORMATION_RSP` (`0x05`) over the range from value handle + 1 to the next declaration/service boundary. Record descriptor handle and UUID; `0x2902` is Client Characteristic Configuration.
4. **Writes/reads/notifications.** Resolve their 16-bit attribute handle through the map. For a notification (`0x1B`) or indication (`0x1D`), the handle is the characteristic value handle. For writes (`0x12` or `0x52`), the handle is also the value handle; do not confuse a CCCD write (`0x2902`) with the vendor command value.
5. **Cache invalidation.** A service change or changed database hash invalidates the map. The GATT specification says clients may cache handles and describes Service Changed/Database Hash invalidation. Source: [Bluetooth SIG GATT attribute caching](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/generic-attribute-profile--gatt-.html).

A useful event record for the evidence bundle is:

```json
{
  "recordIndex": 123,
  "timestampMicros": 0,
  "direction": "outgoing",
  "hciType": "ACL",
  "connectionHandle": 64,
  "attOpcode": "WRITE_COMMAND",
  "attributeHandle": 42,
  "serviceUuid": "...",
  "characteristicUuid": "...",
  "valueHex": "...",
  "originalLength": 31,
  "includedLength": 31,
  "annotation": "vendor action: brightness 50%"
}
```

The event schema is an implementation recommendation **[INFERENCE]**; preserving raw record bytes, decoded fields, source mode, Android build, and SHA-256 hashes is more important than a particular JSON naming choice.

## 5. Android-native GATT MITM/proxy feasibility

### What public APIs provide

**[PROVEN]** Android exposes a GATT central client through `BluetoothGatt`/`BluetoothDevice.connectGatt`, and a local GATT server through `BluetoothGattServer`. The server API provides `addService`, `sendResponse`, `notifyCharacteristicChanged`, and callbacks for remote reads/writes/connections. Sources: [BluetoothGatt](https://developer.android.com/reference/android/bluetooth/BluetoothGatt), [BluetoothGattServer](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer).

**[PROVEN]** Android exposes BLE advertising through `BluetoothLeAdvertiser`. Legacy advertising is limited to 31 bytes of advertisement data; a scan response is a separate `AdvertiseData`. API 26 adds extended advertising sets, subject to controller capability. Sources: [BluetoothLeAdvertiser](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser), [AdvertiseData](https://developer.android.com/reference/android/bluetooth/le/AdvertiseData).

A conceptual tablet proxy is therefore possible:

```text
iPhone central ──BLE link A──> Android BluetoothGattServer
                                   relay/state machine
Android BluetoothGatt client <──BLE link B── gadget peripheral
```

It must clone the observed advertising fields, recreate services/characteristics/descriptors, map iPhone-side handles/UUIDs to gadget-side UUIDs, relay reads/writes, subscribe to gadget notifications, and issue notifications to iPhone.

### Hard limits

- **No public MAC spoofing API. [INFERENCE]** Android advertiser APIs expose data/settings and an own-address type, not an arbitrary source MAC. Gattacker’s BlueZ prior art requires a dedicated `bdaddr` helper to clone the original address, demonstrating why Linux/BlueZ hardware is used for this job. Sources: [BluetoothLeAdvertiser](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser), [Gattacker README](https://raw.githubusercontent.com/securing/gattacker/master/README.md).
- **Handles are stack-assigned. [INFERENCE]** `BluetoothGattServer.addService` accepts a service model and does not let the app choose ATT handles. The relay must map by UUID and operation semantics, not assume iOS sees the gadget’s original handles. Source: [BluetoothGattServer](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer).
- **No raw ATT injection. [INFERENCE]** The public server/client APIs expose GATT operations, not arbitrary raw ATT PDUs or controller packets. Raw HCI/ATT MITM behavior belongs below the public Android API. Sources: [BluetoothGatt](https://developer.android.com/reference/android/bluetooth/BluetoothGatt), [BluetoothGattServer](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer).
- **Address/cache identity matters. [PROVEN]** GATT clients may cache handles for a trusted relationship and use Service Changed or Database Hash to invalidate them. **[INFERENCE]** An iPhone that remembers the original peripheral identity may retain stale service data when presented with a clone using another address; expect to clear pairing/cache or ensure the clone’s database is identical. Source: [Bluetooth SIG GATT caching](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/generic-attribute-profile--gatt-.html).
- **Pairing/security keys cannot simply be cloned. [PROVEN]** ATT attributes can require authentication, encryption, or authorization and return errors such as Insufficient Authentication (`0x05`) or Insufficient Encryption (`0x0F`). **[INFERENCE]** A tablet GATT server cannot transparently reuse the gadget’s existing link keys through these public APIs; secure vendor commands may fail unless the proxy performs a new compatible pairing/security flow. Source: [Bluetooth SIG ATT security](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/attribute-protocol--att-.html).
- **Concurrent roles are not guaranteed. [PROVEN]** The GATT specification allows client and server roles concurrently in the same device. **[INFERENCE]** Whether one Android controller supports simultaneous central and peripheral links, advertising, and the required connection count is chipset/firmware/OEM dependent; gate the feature on runtime tests and expose a clear unsupported result. Source: [Bluetooth SIG GATT roles](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/generic-attribute-profile--gatt-.html).
- **MTU/fragmentation changes timing and packet sizes. [PROVEN]** Android 14 requests ATT MTU 517 for the first GATT client requesting MTU on an ACL connection and disregards subsequent requests; usable characteristic payload is MTU minus protocol headers. Sources: [Android 14 behavior changes](https://developer.android.com/about/versions/14/behavior-changes-all), [Bluetooth SIG ATT](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/attribute-protocol--att-.html).

### Prior art

**[PROVEN]** Gattacker uses separate Noble central and Bleno peripheral HCI devices, a WebSocket relay, service JSON, hooks for dynamic read/write/notify, MAC cloning helpers, and dump/replay. Source: [Gattacker README](https://raw.githubusercontent.com/securing/gattacker/master/README.md).

**[PROVEN]** BtleJuice documents an interception core and proxy on independent machines with two Bluetooth 4+ adapters, target selection, displayed intercepted GATT operations, replay, hooks, and export. Source: [BtleJuice README](https://raw.githubusercontent.com/DigitalSecurity/btlejuice/master/README.md).

These projects are evidence that a two-radio proxy is practical, but they do not prove that Android’s single public Bluetooth stack can provide the same transparent behavior.

## 6. Concrete gadget/protocol prior art

### iDotMatrix

**[PROVEN]** `derkalle4/python3-idotmatrix-library` explicitly reverse-engineers the Android app package `com.tech.idotmatrix`, supports 16×16 and 32×32 displays, scans names beginning `IDM-`, and uses Bleak. Source: [library README](https://raw.githubusercontent.com/derkalle4/python3-idotmatrix-library/main/README.md).

The published UUID constants are:

```text
service/write characteristic: 0000fa02-0000-1000-8000-00805f9b34fb
read characteristic:         0000fa03-0000-1000-8000-00805f9b34fb
device-name prefix:          IDM-
```

Source: [idotmatrix/const.py](https://raw.githubusercontent.com/derkalle4/python3-idotmatrix-library/main/idotmatrix/const.py).

The companion client documents concrete commands such as clock mode, display text, full-screen color, pixel color, and image writes. Source: [python3-idotmatrix-client README](https://raw.githubusercontent.com/derkalle4/python3-idotmatrix-client/main/README.md). This is strong prior art for BLE Studio’s “label/replay/export” workflow, but it does not establish that the owner’s clock is iDotMatrix.

### Glance Clock

**[PROVEN]** `Hypfer/glance-clock` reverse-engineers a BLE wall clock with a 32×8 matrix and four 48-LED rings. It documents service UUID `5075f606-1e0e-11e7-93ae-92361f002671`, characteristic UUID `5075fb2e-1e0e-11e7-93ae-92361f002671`, PIN pairing, protobuf serialization, and command-plus-payload writes. Source: [Glance Clock Readme.md](https://raw.githubusercontent.com/Hypfer/glance-clock/master/Readme.md).

This is useful precedent for storing a GATT map plus decoded higher-layer payloads; the UUIDs and protobuf command IDs are device-specific and must not be generalized.

### Divoom caveat

**[PROVEN]** Divoom Timebox/Timebox Evo/Ditoo protocol projects document Bluetooth Classic/RFCOMM or serial-style communication rather than BLE. The Home Assistant integration warns that an ESPHome BLE proxy does not work because these devices use Bluetooth Classic. Sources: [node-divoom-timebox-evo](https://github.com/RomRider/node-divoom-timebox-evo), [hass-divoom](https://github.com/d03n3rfr1tz3/hass-divoom).

Therefore, identify the target’s transport before implementing BLE assumptions: advertisement/GATT UUIDs imply BLE; RFCOMM/SPP or classic pairing implies a different capture/parser path.

## Recommended capture strategy ranking

### 1. If the vendor app has an Android version: A — full local HCI snoop + Shizuku bugreportz

Use the Android phone with the vendor app, set **Full**, restart Bluetooth, perform one action at a time, and pull `bugreportz -s` through the tablet’s Shizuku UserService. Run the AOSP btsnooz decoder, then parse standard btsnoop. This is the lowest-risk and highest-fidelity path because it observes the vendor app’s own host/controller boundary and does not require MAC spoofing. **[PROVEN]** capture/extraction mechanics; “highest fidelity” is an engineering recommendation.

### 2. If the vendor app is iOS-only: B — two-radio hardware proxy/MITM

Use two independent BLE adapters/radios with BlueZ/Gattacker/BtleJuice-style central and peripheral roles. The iPhone connects to the clone while the proxy connects to the real gadget; relay and log decoded GATT operations. This is the practical path for iOS traffic and permits plaintext observation on each proxied link, but pairing, MAC identity, caching, and secure vendor protocol checks can still defeat a transparent clone. Sources: [Gattacker](https://raw.githubusercontent.com/securing/gattacker/master/README.md), [BtleJuice](https://raw.githubusercontent.com/DigitalSecurity/btlejuice/master/README.md).

### 3. C — single Android tablet central+peripheral relay

Implement `BluetoothGatt` + `BluetoothGattServer` + `BluetoothLeAdvertiser` behind a runtime capability check. It is valuable as an exploratory experiment and may work with a permissive gadget, but public Android APIs do not provide raw ATT injection or arbitrary MAC cloning, and concurrent-role/controller support is not guaranteed. Treat failure to satisfy iOS discovery, pairing, or caching as a platform limitation, not a parser bug. Sources: [BluetoothGatt](https://developer.android.com/reference/android/bluetooth/BluetoothGatt), [BluetoothGattServer](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer), [BluetoothLeAdvertiser](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser).

### Evidence-bundle minimum

Export the original bugreport zip, extracted btsnooz/btsnoop bytes, SHA-256 hashes, Android build/API level, snoop mode/property, adapter role/address information available to the app, capture start/end times, GATT discovery map, parsed event NDJSON, and the operator’s action labels. Keep a clear distinction between **observed bytes**, **decoded protocol fields**, and **human annotations**. This bundle design is an implementation recommendation **[INFERENCE]**, grounded in the loss/truncation fields and replay/export workflows documented by [AOSP btsnooz](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/tools/scripts/btsnooz.py), [NCC BLE-Replay](https://raw.githubusercontent.com/nccgroup/BLE-Replay/master/btsnoop/README.md), and [BtleJuice](https://raw.githubusercontent.com/DigitalSecurity/btlejuice/master/README.md).
